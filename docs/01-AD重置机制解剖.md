# 反物质维度（Antimatter Dimensions）重置机制解剖

> 源码：`ref/AD/`（来自 `IvarK/AntimatterDimensionsSourceCode`，master 分支，31 MB 完整工程）
> 本文只做一件事：把 AD 的"多层重置"拆成可以照抄的结构，供我们自己的增量游戏设计使用。
> 所有行号对应 `ref/AD/` 内文件。

---

## 1. 重置链总览

AD 实际有 **6 个递进层 + 1 条终局支线**，层与层之间是"上级重置 = 下级全清 + 本级给新货币"的严格嵌套关系。

| # | 层 | 触发动作 | 门槛 | 产出货币 | 索引概念 |
|---|---|---|---|---|---|
| L0 | 生产 | — | — | 反物质 AM | 维度 1–8，tickspeed |
| L1 | 软重置 A | **Dimension Boost** | 已购维度数量 | 无（给 AD 倍率 + 解锁新维度） | `dimensionBoosts` |
| L2 | 软重置 B | **Antimatter Galaxy** | AD8 总量 ≥ 递增成本 | 无（降低 tickspeed 成本/提升速度） | `galaxies` |
| L3 | 软重置 C | **Sacrifice** | 5 个 Dim Boost + 有 AD8 | 无（永久倍率） | `sacrificed` |
| L4 | 硬重置 1 | **Big Crunch（Infinity）** | `maxAM ≥ 1.8e308` | **IP** + Infinity 维度 | `infinities` |
| L5 | 硬重置 2 | **Eternity** | 本 etern 内 `maxIP ≥ requiredIPForEP(1)` | **EP** + 时间维度 + 时间研究 | `eternities` |
| L6 | 硬重置 3 | **Reality** | `maxEP.exponent ≥ 4000` 且买了 Reality 研究 | **RM** + Glyph + Perk | `realities` |
| L7 | 终局支线 | Celestials / Pelle | 各不相同的平行条件 | 专属资源 | `celestials.*` |

关键设计点：**L1–L3 是同层内的"软重置"（同一货币体系内循环），L4–L6 才是"层间跳转"（换货币体系 + 清空下层所有进度）。** 玩家的时间感来自这个区别：软重置几秒一次，硬重置几分钟到几小时。

## 2. 每层到底保留什么、清空什么

这是 AD 最值得抄的东西：**每一层都有一份显式的"清空清单"，而且清空清单是靠"调用下级重置函数"而不是手工逐条清字段实现的。**

### L4 Big Crunch

入口 → [`big-crunch.js:49`](../ref/AD/src/core/big-crunch.js#L49) → 清空逻辑 [`secondSoftReset()`](../ref/AD/src/core/big-crunch.js#L154)

```
清空：dimensionBoosts=0, galaxies=0, AM, 全部 AD, Infinity 维度, replicanti(=1),
      thisInfinity 的计时与 maxAM、成就计时器
保留：IP、infinities、Infinity 升级、成就、replicanti 的 unlocked 标记
例外：Achievement(95) 保留 replicanti 数值；TimeStudy(33) 保留一半 RG
```

注意最后那条"例外"——**保留项是通过 `if (成就) 恢复` 写成的，不是通过配置表**。AD 用这种硬编码换取可读性，代价是后期维护痛（源码里 `big-crunch.js:123-125` 的注释就在吐槽这点）。我们做新游戏应该反过来：**保留规则写进数据表**。

### L5 Eternity

入口 [`eternity.js:67`](../ref/AD/src/core/eternity.js#L67)。清空清单长得多，因为它跨了 3 个货币体系：

```
清空：IP、Infinity 维度、replicanti、挑战进度与当前挑战、time dimensions、
      tickspeed、Time Study（除非 respec 逻辑）、dilation、sacrificed、IPMultPurchases
保留：EP、eternities、eternity 升级、成就、里程碑
软重置到起点：dimensionBoosts = 0（若达里程碑则 4）、galaxies = 0（若达里程碑则 1）
```

里程碑是这里最优雅的机制：`EternityMilestone.keepInfinityUpgrades.isReached` 直接改变"起点值"而不是写 if-else 分支（[`eternity.js:193`](../ref/AD/src/core/eternity.js#L193)）。**"永久解锁 = 重置后起点更高"比"永久解锁 = 跳过某段流程"更好平衡。**

### L6 Reality

入口 [`reality.js:586 finishProcessReality()`](../ref/AD/src/core/reality.js#L586)，约 140 行连续清空。它把前面所有东西全部清掉，只留 `realities`、RM、perkPoints 和 Glyph 背包。

结构上有个细节值得抄：**`finishProcessReality` 的第一件事是 `secondSoftReset(false)`（[`reality.js:709`](../ref/AD/src/core/reality.js#L709)）**，即"重演一遍 Big Crunch"，而不是把 Big Crunch 的字段再抄一遍。级联调用，单一职责。

## 3. 四个引擎级抽象

### 3.1 Currency：货币 = 值 + 运算 + 起点

[`currency.js:106`](../ref/AD/src/core/currency.js#L106)。每个货币是一个对象，只暴露 `value` / `add` / `subtract` / `reset()`，`reset()` 的语义是"回到 `startingValue`"。而 `startingValue` 是 **getter**，可以依赖成就、Perk、里程碑：

```js
// currency.js:234
get startingValue() {
  return Effects.max(10, Perk.startAM, Achievement(21), ...).toDecimal();
}
```

于是"永久升级让你开局有更多资源"这件事，零散代码全部消失，只剩一个 getter。

**可复用结论：所有资源的"下限"必须是一等公民，不能写死 0。**

### 3.2 softReset：级联重置的唯一入口

[`dimboost.js:177`](../ref/AD/src/core/dimboost.js#L177)。签名 `softReset(tempBulk, forcedADReset, forcedAMReset, enteringAntimatterChallenge)`，四个参数全是为了"这一层要不要顺便重置下层"。所有上层重置都通过它来清空下层：

- Galaxy → `softReset(0)`（[`galaxy.js:128`](../ref/AD/src/core/galaxy.js#L128)）
- Big Crunch → `secondSoftReset` → `softReset(0, true, true)`（[`big-crunch.js:159`](../ref/AD/src/core/big-crunch.js#L159)）
- Reality → `secondSoftReset(false)`（[`reality.js:709`](../ref/AD/src/core/reality.js#L709)）

### 3.3 EventHub：BEFORE / AFTER 双钩子

每个重置都有 `*_RESET_BEFORE` 和 `*_RESET_AFTER`（`GAME_EVENT`）。用处：

- 自动购买器在 BEFORE 里读"重置前的数值"（算本轮收益）
- UI/成就/统计数据在 AFTER 里刷新
- 特殊机制（Pelle 的 strikes）挂在 AFTER

**这是把 200 多个成就和 100 多个升级挂到重置流程上而不产生循环依赖的关键。**

### 3.4 resetRequirements：需求的级联失效

[`player.js:989`](../ref/AD/src/core/player.js#L989)。每个 `requirementChecks` 记录"本轮是否满足某个隐藏条件"（比如"没买过任何 Infinity 升级就完成 Reality"），重置时用 **switch 穿透** 级联失效：

```js
switch (key) {
  case "reality": player.requirementChecks.reality = {...};
  // fallthrough
  case "eternity": player.requirementChecks.eternity = {...};
  // fallthrough
  case "infinity":  player.requirementChecks.infinity = {...};
}
```

一次调用 `resetRequirements("reality")` 清掉三层。这个技巧直接可抄。

## 4. 数值公式：怎么让 10 个数量级不失控

AD 的全部数值都建立在 **log10 空间里的线性缩放** 上。这是它能撑到 `1e1e9` 还不出问题的原因。

### 4.1 升级阶梯

| 重置 | 公式 | 代码 |
|---|---|---|
| IP 收益 | `10^(log10(maxAM)/308 − 0.75) × 总IP倍率` | [`game.js:89`](../ref/AD/src/game.js#L89) |
| EP 收益 | `5^(log10(maxIP+当轮IP)/308 − 0.7) × 总EP倍率` | [`game.js:138`](../ref/AD/src/game.js#L138) |
| EP 反解 | `10^(308 × (log₅(n/mult) + 0.7))` | [`game.js:156`](../ref/AD/src/game.js#L156) |
| RM 收益 | `1000^(log10(maxEP)/4000 − 1)`，硬上限 1e1000 | [`machines.js:19`](../ref/AD/src/core/machines.js#L19) |
| Glyph 等级 | 4 个源相乘：EP^0.5、Replicanti^0.4、DT^1.3、Eternities^0.45 | [`auto-glyph-processor.js:232`](../ref/AD/src/core/glyphs/auto-glyph-processor.js#L232) |

规律：**每一层的收益 = 上一层的"最大成就"取 log，除以一个固定常数，再指数化。** 常数（308 / 4000）是节奏旋钮——调大它，本层变慢；它是该层"需要多少个数量级才能进下一层"的直接编码。

> 308 = `log10(1.8e308)`，即 double 上限。AD 反复用这个数，因为 Big Crunch 的门槛就是"撞到浮点上限"。

### 4.2 软上限：把线性增长折成平方

[`auto-glyph-processor.js:334`](../ref/AD/src/core/glyphs/auto-glyph-processor.js#L334)，这是全工程最值得抄的一个函数：

```js
const instabilitySoftcap = (level, begin, rate) => {
  if (level < begin) return level;
  const excess = (level - begin) / rate;
  return begin + 0.5 * rate * (Math.sqrt(1 + 4 * excess) - 1);
};
```

超过 `begin` 后，每 +1 有效等级需要的原始等级越来越多（线性 → 二次）。AD 把它**叠加两次**（instability + hyperInstability，begin 和 rate 不同），得到"阶段式递减"。这比"直接封顶"体验好得多：玩家永远有收益，只是边际递减。

### 4.3 反解函数必须存在

`requiredIPForEP(1)`（[`game.js:156`](../ref/AD/src/game.js#L156)）是 `gainedEternityPoints` 的代数反解，用来显示"还差多少"。**只要有收益公式，就必须写反解**，否则 UI 无法显示"距离下次重置还差 X"。这是 AD 里最容易被忽略但最影响体验的一条。

## 5. 数据驱动：secret-formula

所有可调内容都在 `src/core/secret-formula/`，约 **40 个数据文件、2.5 万行**，包括 1384 行成就、1987 行新手引导、690 行时间研究、456 行炼金。

入口 [`game-database.js:24`](../ref/AD/src/core/secret-formula/game-database.js#L24)，聚合后由 `mapGameDataToObject` 变成"按 id 索引的对象 + `all` 数组"。单条配置长这样（[`eternity-upgrades.js:11`](../ref/AD/src/core/secret-formula/eternity/eternity-upgrades.js#L11)）：

```js
idMultEternities: {
  id: 2,
  cost: 10,
  description: () => `...(softcap at ${format(1e5)} Eternities)`,
  effect() { /* 返回数值 */ },
  formatEffect: value => formatX(value, 2, 1)
}
```

`effect` 是**函数而非值**，每次读取时实时求值——这消灭了"缓存失效"这一整类 bug。`formatEffect` 与 `description` 也放数据里，所以 UI 不需要知道任何升级的存在。

**可复用结论：效果永远写成从状态求值的纯函数，绝不缓存；显示格式跟着数据走。**

## 6. 踩过的坑（源码里明确记录过的）

| 坑 | 位置 | 教训 |
|---|---|---|
| 保留项硬编码在重置函数里 | `big-crunch.js:123` | 保留规则必须数据化 |
| 重置顺序影响正确性 | `reality.js:642`（`epMult.reset()` 必须在 `eternities.reset()` 前） | 重置要有明确拓扑序，级联优于平铺 |
| 模拟 N 次现实会卡死弱设备 | `reality.js:378`（>100 次改走采样 + 进度条） | 批量结算必须采样或异步，不能同步跑循环 |
| RNG 因触发时机不同而发散 | `reality.js:202`、`auto-glyph-processor.js` | 批量奖励要"先生成后选择"，不能按玩家选择顺序消耗随机数 |
| 反解公式缺失导致 UI 无法显示进度 | `game.js:156` | 收益公式与反解要成对写 |
| 存档字段爆炸 | 1089 行 `player.js` 默认值 | 迁移成本极高；我们的存档结构要版本化 + 迁移函数 |

## 7. 我们自己的游戏要先定的 12 个变量

写设计时按这个清单填，填完就能直接映射到代码结构（配套模板见 `02-游戏设计文档-骨架.md`）。

1. **层数**：几层重置？1–3 层是短局，5+ 是 AD 式长局。
2. **每层的名字与产出货币**。
3. **每层的触发条件**（数值门槛 / 手动按钮 / 混合）。
4. **每层的收益公式**，以及它的反解。
5. **每层的保留清单**（哪些东西跨过这层重置还活着）。
6. **"起点值"机制**：哪些永久升级提高下层资源的开局下限。
7. **层内软重置有多少种**（AD 有 Boost / Galaxy / Sacrifice 三种）。
8. **加速层**：AD 用 tickspeed 与 replicanti，我们用不用？怎么和主循环耦合？
9. **并行支线**（Celestials 式）：是否允许"不推进主线也能玩"的内容。
10. **自动化节奏**：第几层开始给自动购买器，给到什么粒度（单买 / 批量 / 满买 / 条件触发）。
11. **批量结算策略**：离线收益、模拟次数上限、采样阈值。
12. **首小时/首日/首周的目标时长曲线**（每层各花多久）。
